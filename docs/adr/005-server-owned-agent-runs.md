# 005 — agent 运行由服务端持有，HTTP 连接只是订阅者

状态: 已采纳 (2026-10)

## 背景

最初实现里，一次 agent 运行的生命周期就是那个 `POST /api/chat/stream` 响应：

```
new ReadableStream({ async start() { await runAgent(...) } })
```

连接一断，运行就随之结束。这在桌面浏览器上勉强能用，但**在手机上是致命的**——
「锁屏 / 切到别的应用 / 系统回收后台标签页」是手机上的日常动作，每一个都会断掉
那个连接。用户会遇到：说一句话，揣兜里，掏出来发现任务没了。

同类问题还有三个，根因相同：

1. 运行中断连 = 运行终止，即使它正等审批；
2. 审批等 180 秒就超时，锁屏三分钟等于静默拒绝；
3. 断连后没有任何地方能查到「我的任务跑到哪了」。

## 选项

1. **保持现状**，只把审批超时调长。不解决问题 1 和 3。
2. **让客户端负责重连**：断连后由客户端重新发起一次请求，带上已收到的进度。
   但服务端并没有任务的持久状态，重新发起等于重跑，会重复产生副作用（重复写文件、
   重复执行命令）。
3. **服务端持有运行，连接只是订阅者**：运行有独立生命周期与事件缓冲，客户端可以
   随时接入 / 断开 / 重新接入并从任意序号回放。

## 决定

采纳选项 3。新增 `src/agent/runs.ts`：

- `RunRegistry` 持有运行记录：状态、事件环形缓冲（上限 4000 条）、订阅者集合、
  待批审批、AbortController。
- 每个事件带单调递增的 `seq`，客户端据此判断收到哪一段。
- `POST /api/chat/stream` 创建运行后**在后台跑**，响应体只是订阅这个运行的流；
  响应的 `ReadableStream.cancel()`（客户端断连）只解除订阅。
- `GET /api/agent/runs/:id?from=N` 一次性拉取状态 + 回放。
- `GET /api/agent/runs/:id/stream?from=N` SSE：先回放再直播，运行结束才收尾。
- `POST /api/agent/runs/:id/cancel` 显式取消——取消是**运行级**的，不是连接级的。
- 运行结束后保留 10 分钟（供客户端回来看到结果），并限制保留数量上限。
- 等审批时可能长时间无事件，所以每 20 秒发一次 SSE 注释心跳，避免空闲连接被
  中间层掐断。

配套改动：

- 审批超时从 180 秒提到 15 分钟（`POCKETD_APPROVAL_TIMEOUT_MS` 可配），仍是 fail-closed。
- 客户端把 `activeRun`（runId + 会话索引）持久化到 localStorage，页面重开时自动接回；
  从 `seq 0` 全量回放重建消息，而不是增量续接——回放幂等，重建不会与旧状态漂移。

## 理由

- 运行的事件流是**幂等可观测量**（工具是否真的执行由工具层的审批决定），
  重放只影响展示，不影响副作用；这使「回放重建」比「增量续接」更安全。
- 环形缓冲 + 保留窗口让内存占用有界，而手机进程本来就不该长期持有大对象。
- `seq` 让客户端能发现自己错过了什么（服务端会回 `truncated`），而不是静默少一段。

## 代价与已知限制

- **运行状态在内存里**：服务端进程重启会丢掉所有进行中的运行。客户端接回时收到 404，
  会明确告知「无法接回上次的任务」并清理标记，不会静默消失。
- 事件缓冲上限 4000 条；超长运行（文本增量极多）会丢弃最旧的事件，客户端收到
  `truncated` 后重建消息体（只保留重放窗口内的内容）。
- 单个进程内不做运行隔离或配额：这是本机自用工具，不是多租户服务。

## 验证

`npm run test:e2e` 的「断连重连场景」逐条断言：断连后运行仍为 `running`、待批审批仍可
查询、重连回放包含 `run-start` 与 `approval-request`、从重连的连接完成审批、工具真实
执行、运行收尾为 `done`、以及显式取消得到 `cancelled`。真实浏览器里也验证过完整路径
（发消息 → 出现审批 → 关页 → 重开 → 批准 → 收到终局输出）。
